# Make the auth browser channel configurable instead of forking or patching the auth package

The spec adopts `playwright-ms-auth` wholesale, including its password-credential path for local development. That package hardcodes `channel: "msedge"` in its browser launch, with no config option and no environment variable to override it. Version 0.0.19 is the latest published, so there is no upstream fix to wait for.

On a corporate-managed Windows device this makes local sign-in impossible. The Edge process exits cleanly the moment the flow lands on `make.powerapps.com/auth` after the "Stay signed in?" prompt — before any storage state is written — and `playwright-ms-auth` fails at its next call with `Target page, context or browser has been closed`. The browser log shows enterprise policy in play (Edge loads an IE-mode sitelist of corporate entries); the most likely mechanism is automatic profile switching relaunching the work URL in the user's real Edge profile and terminating the automation instance. The same flow, byte for byte, completes on Playwright's bundled Chromium: 23 cookies, 41 localStorage entries, and the maker portal reached signed in.

`MS_AUTH_BROWSER_CHANNEL` now selects the browser for the sign-in flow. When it is unset — the default — `authenticateToMicrosoft` delegates to `playwright-ms-auth`'s `authenticate()` exactly as before, so upstream behaviour is unchanged for anyone not affected. When it is set, a fork-owned `signInWithChannel` drives the same flow, reusing the package's own credential providers (`CredentialProviderFactory`) and storage-state paths so only the browser launch differs. It supports password credentials only and throws a clear error for certificate credentials, which remain on the upstream path; CI uses certificates on unmanaged agents, where the problem does not arise.

Three alternatives were rejected. **Patching the dependency** (npm `overrides` or `patch-package`) keeps repo source byte-identical to upstream, but pins the fork to the internals of a 0.0.x package and requires re-applying the patch on every bump. **Fixing Edge policy** depends on corporate configuration the team does not control, and would leave the repo broken for any other consumer on a managed device. **Leaving it broken** and waiting for upstream blocks local development indefinitely on a package that has shipped four versions without making this configurable.

Note that this is only a problem for the auth step. The tests themselves already run on bundled Chromium — `playwright.config.ts` sets `browserName: 'chromium'` with no channel — so selecting `chromium` for auth makes the sign-in browser and the test browser agree rather than diverge.

Decided during the fork bootstrap, [issue #22](https://github.com/jimiryquai/power-platform-playwright-xrm-toolkit/issues/22).
